# TWD Site Kit

A WordPress plugin, sibling to the Articles & Resource Production Plugin (`twd-article-publisher`, in `thistwistedyouth/therapy-web-designs`). It lets a whole therapist site (its pages and styles) be built and remixed with AI, using copy and paste, without an API key on the client site. This file is the short version: rules, not stories. **HISTORY.md** has the reasoning behind each decision and the open questions.

Target site: Hello theme + Elementor (header and footer only) + Articles plugin + Site Kit.

## Names (never rename)

- Folder, main file, text domain: `twd-site-kit`
- Class prefix: `TWD_SK_`. REST namespace (later): `twd-site-kit/v1`. CSS classes: `twd-sk-`. Options and meta: `twd_sk_` (post meta keys start with an underscore: `_twd_sk_html`, `_twd_sk_versions`). CSS variables (later): `--twd-site-*`.
- Minimum: PHP 7.4, WordPress 6.0. No PHP 8-only syntax or functions in plugin code (a test checks).

## Style

Vanilla JS, no build step, no Composer, tabs, snake_case, same style as the articles plugin. No em dashes or en dashes anywhere, including comments (use hyphens). A test checks source files.

## Architecture rules

- **A page is sanitised HTML using allowed classes.** It is not a typed component tree and not a custom post type. The HTML and its history live in post meta on the WordPress page that holds `[twd_page]`.
- **`TWD_SK_Registry`** is data only. One entry per component, keyed on its ID, never on the display label: `hero`, `text`, `image_text`, `quote`, `faq`, `services`, `steps`, `cta`, `contact`, `notice`, `resources`. Each has `id`, `label`, `description`, `skeleton` (the default variant), `variants` (modifier class => label and full skeleton), `classes` (every class it may use, modifiers included) and `shortcodes`. `shared_classes()` holds the classes any component may use (containers, tones, type, buttons, cards). It renders nothing. It feeds the sanitiser allowlists, the gallery generator and (later) the AI style guide. To add a component or variant, add it to the registry and write its CSS; tests check every skeleton survives the sanitiser untouched, every class is styled, and the gallery is regenerated.
  - Placeholder text in skeletons is plain words, never square brackets (the sanitiser removes `[like this]` as a shortcode) and never real details. Emails use `you@example.com`, phones `PHONE_NUMBER`, pictures `/wp-content/uploads/your-image.jpg`.
  - Variants: hero split, image, compact; text aside; image_text reverse, narrow, badge, band; quote cards, pullout; services cards, pills; cta band, strip; contact split. `team` was folded into `image_text` (badge variant). A contact form is never part of the page HTML.
  - **`notice`** is a safety note plus a helpline modal, pure CSS with `:target` (a link to `#twd-sk-helplines`, a close link back to `#twd-sk-notice`). No JavaScript. Text-message numbers are shown as plain text, never `sms:` links. The helpline list must be verified against official sources before any site launches.
- **`TWD_SK_Sanitizer`** is the only path HTML takes into storage. Fully independent of the articles plugin: its own `strip_dashes()`, no calls into any `TWD_AP_*` code (a test checks). No WordPress functions inside it, so it runs in plain PHP. `clean()` returns HTML, `clean_with_report()` also returns what was removed.
  - Removed with contents: script, style, iframe, object, embed, form controls, svg, math, video and similar. Unknown tags are unwrapped.
  - **One h1 per page.** An `h1` stays only if it has the class `twd-sk-hero__title`, sits inside an element with the class `twd-sk-hero`, and is the first such h1 in the page. Every other `h1` becomes `h2` (and is reported). The check happens after class filtering, so a made-up class cannot earn it. The allowance resets on every `clean()` call.
  - Attributes kept: `class`, `id` (only `twd-sk-` prefixed), `href`/`target`/`rel`/`title` on links, `src`/`alt`/`width`/`height`/`title` on images, `open` on details. Everything else goes (every `on*`, `style`, `data-*`).
  - Classes: only those in the registry. Case-sensitive, exact.
  - Links and images: http, https, mailto (links only), tel (links only), relative paths, `#anchors`. Protocol-relative (`//host`, `/\host`) is refused. An image with no valid src is dropped.
  - Shortcodes: all removed except those in the registry (`twd_articles`), which are rebuilt with validated attributes only. `[twd_page]` is never allowed.
  - Dashes: em and en dashes become a comma, or are dropped before closing punctuation. Applied to text and `alt`/`title`, not to URLs.
  - The parser needs the UTF-8 meta tag in the wrapper or it mangles accents and emoji (tests cover curly quotes, pound sign, accents, emoji). The serialiser percent-encodes non-ASCII in `href`/`src`, which is the same URL.
  - Elements are rebuilt from their surviving attributes. `removeAttribute()` cannot remove attributes with a colon in the name, so never switch back to removing in place.
- **`TWD_SK_Store`** is the only writer of the two meta keys. Append-only, cap of 10 versions per page, 200 KB per page. Restore and undo write a new version. Identical HTML is a no-op. Empty result is refused. Optional `base_version` refuses a write if the page has moved on (for the deploy workflow later). Always `wp_slash()` before `update_post_meta()`. No capability checks in the store; the REST layer and WP-CLI decide who may call it. There is no draft row: the human gate is Preview then Apply with Undo (later slice), built on this API.
- **Title hiding.** If a page's stored HTML contains an h1, `TWD_SK_Page` hides the theme's own page title: the Hello filter `hello_elementor_page_title` returns false (server side, no flash), and the body class `twd-sk-has-h1` is added for other themes. Only single pages are affected, and only when an h1 is stored, so a page never has zero h1s and never two. The stylesheet's last rule hides `.page-header` and `.entry-title` under that body class: the one rule allowed outside the `.twd-sk-page` wrapper.
- **`TWD_SK_Packs`** (style packs and tokens). A pack is a JSON file in `packs/` holding design tokens only (colours, two fonts, radii, spacing, button style, image position), never CSS or markup. Every value is validated against a strict pattern (hex or rgb colours, plain non-negative lengths with px, rem, em or %, known weights, bundled fonts only, strict shadows and positions), so a pack or an override cannot inject anything else. A pack must define every token. Tokens print as `:root{--twd-site-*:...}` (inert on their own); all rules live in the stylesheet. Active pack: option `twd_sk_pack` (default `sage`). Per-site overrides: option `twd_sk_tokens`, validated the same way, invalid entries ignored. Switch with `wp twd-sk pack <slug>`.
  - Packs are built from the final cascaded look of the reference sites, not the first rules. "sage" shows no second colour on the heading accent span (accent colour equals heading colour); "grove" shows a sage italic accent.
  - Both packs meet 4.5:1 for every pair the components use (a test lists them), and the size floors hold (body and lead 16px, small text, eyebrows and buttons 14px; pack validation rejects smaller). The packs are therefore slightly darker than the two reference looks. HISTORY.md has the detail.
- **Fonts** are bundled in `assets/fonts` (Cormorant Garamond, Lora, Jost, Nunito: variable woff2, Latin subset, SIL Open Font Licence, licence text beside the files) so client sites make no requests to Google Fonts. Only the two fonts the active pack uses are declared with `@font-face` (`font-display: swap`). A pack may instead use "System serif" or "System sans" and ship no font files. Adding a font means adding the file, its licence and an entry in `TWD_SK_Packs::fonts()`.
- **Stylesheet** (`assets/twd-site-kit.css`, loaded on every front-end page because Elementor hides shortcodes from `has_shortcode()`). Rules enforced by `tests/test-css.php`: every selector scoped under `.twd-sk-page` (one exception, the title fallback); every component class doubled in its selector so a theme cannot win on specificity; `!important` on every visual property (colour, background, font, border, padding, margin, radius, shadow, text) but never on layout, so the unconditional `[hidden]` rule always wins; no colour or font literals (tokens only); no `100vw`, no negative margins, no `overflow: hidden` (the wrapper uses `overflow-x: clip`); every registry class is styled and no unregistered class is. Image rows are CSS Grid with `align-items: stretch`, images `width: 100%; height: 100%; object-fit: cover; object-position: var(--twd-site-image-position)`, never flex. A page sits in a full-width Elementor container with no padding. A contact form is an Elementor widget placed in a container that has the CSS class `twd-sk-page`; the "form skin" rules at the end of the stylesheet then skin it with the pack. **The stylesheets are generated.** Edit `tools/kit.src.css` (page styles, scoped under `.twd-sk-page`) or `tools/editor.src.css` (the pop-up, scoped under `.twd-sk-ed`); selectors are relative to the wrapper, `$token` for tokens. Run `python3 tools/build-css.py` and commit the sources and both generated files. A test fails if a committed stylesheet differs from what the script builds. Do not edit the generated file by hand. The zip ships only the generated file.
- **`TWD_SK_Updater`** (self-hosted updates, admin only). Reads `dist/twd-site-kit-update.json` from this PUBLIC repo on `main` (raw.githubusercontent.com, no credentials), caches the cleaned result for 12 hours in the `twd_sk_update_check` transient, and shows a normal update row, "View details" changelog and one-click update. A "Check for updates" link on the plugin's row on the Plugins screen clears the cache, forces core to recheck, and shows the result. Stricter than the articles plugin's updater:
  - Only two addresses are ever fetched, both fixed https constants in the class (`JSON_URL`, `ZIP_URL`), with no redirects followed. The package address is never read from the JSON: a JSON that names any other address is ignored.
  - The JSON must carry a `sha256` of the zip. An update with no valid checksum is never offered. At install time (`upgrader_pre_download`) the JSON is fetched fresh, the zip is downloaded by the updater, hashed, and refused unless it matches. Any doubt fails closed with a plain message ending "Nothing was changed". A version that is not newer than the installed one is refused, so there is no silent downgrade.
  - After unpacking (`upgrader_source_selection`) the package must be the single folder `twd-site-kit` holding the plugin file.
  - Nothing is hooked unless `is_admin()`.
  - The checksum protects against a corrupted, partial or stale download and a tampered zip. It is not a signature: anyone who can push to this repo can change both the zip and the JSON, so keep two-factor authentication on the GitHub account.
- **Gallery.** `starters/_gallery.html` shows every component and variant once. It is generated from the registry by `php bin/build-gallery.php` and a test fails if it differs. It must pass the sanitiser with nothing removed. Later hero variants use an h2 title because a page has one h1.
- **Privacy guard** (`tests/test-privacy.php`). This repo is public. Generic checks always run (real-looking emails, phone numbers, web addresses, upload paths, long digit runs; other agency repos and client site repos are never named). A private list of client words kept OUTSIDE the repo is checked when present: set `TWD_SK_PRIVACY_DENYLIST` to a file with one word per line, or put it at `~/.twd-sk-privacy-denylist.txt`. Run the suite with the list before every push.
- **Front-end editor (slice 3b).** A signed-in user who can edit pages sees an "Edit with AI" button (bottom left) on a kit page they can edit; it opens a pop-up. The AI itself is never called: the therapist copies the prompt (`TWD_SK_Prompt`), pastes the result, previews it, applies it. Files: `TWD_SK_Editor` (loads the button, `assets/twd-site-kit-editor.js` and `.css`, only for editors, never for visitors, wp-admin, the preview frame, Elementor's editor or the customizer), `TWD_SK_REST` (routes), `TWD_SK_Preview` (draft previews), `TWD_SK_Report` (the cleaning report in plain English).
  - **REST namespace `twd-site-kit/v1`**, routes under `/pages/{id}/`: `prompt` and `versions` (GET); `preview`, `preview/discard`, `apply`, `undo`, `restore` (POST). Every route needs a valid `X-WP-Nonce` (checked again in our own permission callback), a signed-in user, `edit_pages` and `edit_post` on that page, a page (not a post), a body under 300 KB, and is rate limited per user (30 writes or previews a minute, 120 reads). Every write goes through `TWD_SK_Store` (so through the sanitiser); the REST class never touches meta, options or the network (a test checks the source). Every write names its `base_version`, so a stale tab gets a 409 instead of overwriting.
  - **Preview**: `POST preview` cleans the paste on the server and keeps the cleaned HTML in a transient under a random 32-character token for 15 minutes (5 per user). The pop-up shows the page's own address plus `?twd_sk_preview=TOKEN` in a frame. On that request `TWD_SK_Preview` swaps the HTML (through the `twd_sk_page_html` filter used by `TWD_SK_Page::current_html()`), only for the user who made it, who must still be able to edit that page; anyone else gets a 403 page. Preview responses are no-cache and noindex, show a "Preview only" bar, and never load the editor script. Nothing is written to the page or its history.
  - **Apply** is allowed with leftover example text (a banner shows the count); only publishing (release 2) is blocked while they remain. The note box ("Where did these facts come from?") is stored as the version's note and shown in the history. The user id is stored on every version (id only).
  - **Pop-up**: vanilla JS, no build step, never `innerHTML` (a test bans it), no `eval`, no native dialogs, no web address in the script. Focus trap, Esc closes, focus returns to the button, full screen with large tap targets under 700px. The clipboard copy falls back to a selected text box.
  - **Stylesheet**: `assets/twd-site-kit-editor.css` follows the same rules as the page stylesheet, scoped under `.twd-sk-ed`, built from `tools/editor.src.css` by the same script.
- **Kit page template and publishing (0.3.1).** `TWD_SK_Template` registers the "TWD Kit Page" template (`theme_page_templates`) and serves `templates/kit-page.php` from `template_include` at priority 99 (so an Elementor Pro single-page template cannot take over a kit page), only for a single page whose `_wp_page_template` is ours. The template calls `get_header()` and `get_footer()` (Hello's header.php and footer.php call `elementor_theme_do_location`, so an Elementor Theme Builder header and footer work), prints a bare `<main id="content">` with no theme wrapper classes, and shows the page title in a compact hero only when the stored HTML has no h1. It never prints `the_content()`. New pages are created as drafts with the template and no content. Switching a `[twd_page]` page to the template refuses until the caller confirms when the page's Elementor layout has other widgets (a form, a map), because they would stop showing. Publish and unpublish need `publish_pages` and `publish_post` on that page and an explicit `confirm`; publishing refuses an empty page and, unless `override_placeholders` is true, a page with "must fix" leftovers (a 409 listing them); the front page and posts page cannot be unpublished. None of this writes page HTML.
  - **Two leftover levels.** "Must fix" (blocks publishing; applying is still allowed) is every leftover marker except the four example link texts, which are "check" (warns only, never blocks). `TWD_SK_Sanitizer::leftover_level()` and `find_leftovers_by_level()` decide; the pop-up banner, the Pages tab and `wp twd-sk check` show both levels. A test checks every marker's level and that each "must fix" marker blocks publishing.
- **Safe mode (0.4.0).** `TWD_SK_Safe::on()` is true when the `TWD_SK_SAFE_MODE` constant is set in wp-config or the option `twd_sk_safe_mode` is on (`wp twd-sk safe-mode on|off|status`). The main file starts `TWD_SK_Modules::init()` (everything added in 0.4.0) only when it is off. Safe mode keeps the 0.3.1 and earlier features working, including the template and Pages tab (a page made with the template would otherwise show blank). `[twd_header]` and `[twd_footer]` stay registered in safe mode and print a minimal plain version. Recovery steps are in BUILD-LOG.md. Anything new in a release must be started from `TWD_SK_Modules` or check `TWD_SK_Safe::on()`.
- **Site tab and style (0.4.0).** Administrators only (`manage_options`), its own script (`assets/twd-site-kit-editor-site.js`, loaded after the main one, never in safe mode), routes under `/site`. `TWD_SK_Site` holds the editable tokens (15 colours, 2 fonts, 3 corner radii) and applies a change: a pack switch clears the old overrides, only values that differ from the pack are stored, every value goes through `TWD_SK_Packs::validate_tokens` (strict patterns, bundled fonts, size floors). `TWD_SK_Contrast` blocks a save (422) when text on a button or a band falls under 4.5:1 (button text on the button colour, on the hover colour, dark text on light buttons, button text on tinted sections, text on bands, accent on bands) and only warns for the weaker pairs; transparent colours are listed as not checked. The browser computes the same ratios (a test runs both) and previews by setting `--twd-site-*` on the root element; nothing is saved until Save. Reset clears the overrides.
- **Site profile, header and footer (0.4.0).** `TWD_SK_Profile` (option `twd_sk_profile`) holds site name, logo (a media library picture), menu (8 items, one level of sub-menu), header button, phone, email, address lines, footer text, legal links, registration lines (only what the client supplied), therapist name and job, professional profile links (https only). Every field is validated (plain text with limits, links through `TWD_SK_Sanitizer::safe_url`, a real email, a logo that must be an image) and a bad one stores nothing. `starter()` fills every field with a `[PLACEHOLDER: ...]` or `PHONE_NUMBER` marker so the leftover check flags it. `TWD_SK_Chrome` prints the header and footer through the `[twd_header]` and `[twd_footer]` shortcodes (registered always, even in safe mode, where they print a plain minimal version, as they do for an empty profile or any failure). Four header layouts (bar, centered, split, minimal) and four footer layouts (columns, band, centered, simple) live in the plugin; a pack names its preferred pair in a `chrome` key (read by `TWD_SK_Packs`, validated), a per-site override is stored in option `twd_sk_chrome`. Options: sticky (fixed to the top with a spacer; not for the centred header), header button, contact strip, footer columns 1 to 3. Legal links always print (a privacy line at minimum, linked only to the page WordPress itself knows), registration lines come only from the profile, the copyright year is printed by PHP. The output sits in a `.twd-sk-page.twd-sk-chrome` wrapper so the kit stylesheet applies; its classes are listed in `TWD_SK_Chrome::classes()`. The mobile menu is `assets/twd-site-kit-header.js` (no inline handlers): with no script the full menu simply shows; once it runs it adds the menu button (`aria-expanded`, Escape closes and returns focus, tabbing out or clicking outside closes). `TWD_SK_Elementor` builds the two Theme Builder templates (one full-width container with one Shortcode widget each); `starters/elementor/*.json` are generated by `bin/build-elementor-templates.php` and a test checks them; `wp twd-sk export-templates` and a Site tab button hand them out.
- **Starter pages and setup (0.4.0).** `TWD_SK_Starters` builds Home, About and Contact from the registry's own skeletons (hero, services, image and text, quote, cta, resources / hero, image and text, text, steps, quote, cta / hero, contact, faq, notice) and turns every piece of sample text, picture description and link wording into a visible `[PLACEHOLDER: ...]` marker (the safety notice keeps its real support lines; shortcodes are left alone). Each page has one h1 (its first hero's title), passes the sanitiser with nothing removed, and is flagged by the leftover check, so the publish block refuses it until the markers are replaced. `starters/page-*.html` are generated by `bin/build-starters.php` and a test checks them. `TWD_SK_Setup::run()` creates the three pages as DRAFTS with the kit template (through `TWD_SK_Template::create_page` and `TWD_SK_Store::save`), marks them with the meta `_twd_sk_starter` so a second run skips them, fills an EMPTY profile with `TWD_SK_Profile::starter()` (never overwriting one with content), optionally switches the pack, and makes Home the front page unless a published static front page is already set. Nothing is published. Entry points: `wp twd-sk setup [--pack=] [--skip-front-page]`, the Site tab button (asks first, listing what will happen), and the routes `GET /site/setup` (the plan, changes nothing) and `POST /site/setup` (needs `confirm`). Setting a draft as the front page shows visitors an error until it is published, so run it on a new site.
- **Articles grid styling.** The resources component wraps the articles plugin's `[twd_articles]` grid. Rules in the stylesheet target that plugin's documented classes (`twd-ap-article-card`, `-title`, `-excerpt`, `-date`, `-readmore`, `twd-ap-articles-group-title`, search, select, load more) under `.twd-sk-page`, doubled, with `!important` on visual properties, tokens only: titles in the heading font and title colour, "Read more" in the accessible accent, text in the body font at the small size (14px or more). Colour, type and shape only; the plugin keeps its layout. Harmless when that plugin is absent. Never modify the articles plugin; a test keeps these rules scoped.
- **Stray content.** A direct child of `.twd-sk-page` that is not a `section` (and not `.twd-sk-inner`) gets the container max-width, auto side margins and gutter padding, so it never touches the viewport edge. The sanitiser wraps loose top-level text in a `p` so CSS can reach it. Sections are untouched.
- **`[PLACEHOLDER]`.** The sanitiser keeps `[PLACEHOLDER]` and `[PLACEHOLDER: some words]` (up to 60 characters) as plain text instead of treating it as a shortcode, so a missing detail stays visible on the page. Every other bracket token is still removed.
- **`TWD_SK_Prompt`** builds the client AI prompt: fixed rules, a style guide generated from the registry (every component, variant and class with an example), and the page's current HTML. `wp twd-sk prompt <page_id>` prints it. Tests check every registry class (except the gallery label, deliberately omitted) and the page HTML appear. A variant identical to its default is not printed twice. For a new image the prompt says to write `[PLACEHOLDER: image needed]` as text where the picture goes (an image address with brackets is refused by the sanitiser), never to invent a file name.
- **Leftover example text.** `TWD_SK_Sanitizer::find_leftovers()` finds registry example text, case-insensitively: sample addresses (`example.com`, `.org`, `.net`, in any form), `PHONE_NUMBER`, sample headings, labels, paragraphs, image descriptions, testimonial, FAQ, topic and description wording, `your-image` and `your-badge` picture names, sample `/service-1` style links (only `href`s of that exact shape, so a real `/service-anxiety` is fine), the example button and link wording from the style guide ("Contact me about a first session", "Find out about my services", "Read more about this approach", "Call me to arrange a first session"), and any `[PLACEHOLDER`. The four example link texts are "check" level: a warning that never blocks publishing. The cleaning report carries the result as `leftovers` (a warning, never counted as a removal, never changes the HTML), the pop-up banner and `wp twd-sk check <page_id>` list it by level, and the publish block uses the "must fix" level. The safety notice is exempt: its real support-line text must stay. A test requires every non-notice example in the registry to be flagged, so a new example needs a marker.
- **`[twd_page]`** takes no attributes and no id, renders the current page's stored HTML in one `div.twd-sk-page` wrapper. Only registry shortcodes run at render time, every other bracket is turned into an entity. It never relies on `has_shortcode()` (it cannot see inside Elementor's JSON), it uses a render-time flag.
- **WP-CLI** (`wp twd-sk save|get|versions|undo|pack|prompt|check`) is loaded only when `WP_CLI` is defined. The page commands go through the store API only; `pack` goes through `TWD_SK_Packs`. It is not the import endpoint.

## CSS rules

See the Stylesheet bullet above. In short: one wrapper class, doubled component classes, `!important` on visual properties only, an unconditional `[hidden]` rule, tokens only, no viewport-width or negative-margin tricks, `overflow-x: clip` not hidden. Restyle means design tokens only, in the `--twd-site-*` namespace.

- **Search basics (0.4.0).** Four small modules, all started from `TWD_SK_Modules` (so all off in safe mode). (1) `TWD_SK_Mirror` keeps a plain-text copy of each kit page on every committed version (hook `twd_sk_committed`): always in meta `_twd_sk_text`, and for a page using the kit template also in the page's own content (the template never prints content, so nothing shows twice; core search, feeds and Yoast then find the words). Content is replaced only when empty or when it is the plugin's own earlier text (checked by a content hash), so a page still holding the `[twd_page]` shortcode, Elementor content or typed words keeps its content and only gets the meta copy. Limitation: such a legacy `[twd_page]` page is not searchable by core search until its content is cleared once after switching it to the kit template. (2) `TWD_SK_Images` adds width and height (media library pictures), a high priority hero picture and lazy loading to every other picture at display time, never stored (the sanitiser strips those attributes on the way in). The footer logo is lazy; the header logo never is. (3) `TWD_SK_Seo` reads and writes title, description, social picture, keep-out-of-search and the slug. Yoast active: writes Yoast's own meta keys and re-saves the page. No SEO plugin: keeps `_twd_sk_seo_*` and prints title, description, Open Graph, Twitter and robots itself. Another SEO plugin (Rank Math, AIOSEO, SEOPress, The SEO Framework): refuses field writes and prints nothing; the slug can still change. Changing the slug of a live page needs `confirm_slug_change`; the front page and posts page cannot change. Routes `GET` and `POST /pages/{id}/seo` (edit permission, not registered in safe mode); the Search tab script is `assets/twd-site-kit-editor-seo.js`. Example text in the title or description joins the leftover check through the `twd_sk_leftover_levels` filter, so it blocks publishing. `TWD_SK_Quality` reports missing alt text, skipped heading levels, vague or empty links and a missing h1 (report only). (4) `TWD_SK_Schema` builds a ProfessionalService and a Person from the profile on the front page only, leaving out anything empty, any `[PLACEHOLDER`, bad contact details; registration lines are never printed. With Yoast it adds the nodes to Yoast's graph (filter `wpseo_schema_graph`, once); with another SEO plugin it prints nothing; with none it prints one script block (JSON with tags, ampersands and quotes hex escaped). The Search tab has a button that checks the open page for the same structured data type printed twice.
- **Edit pills and the unsaved prompt (0.4.1).** `twd-site-kit-editor-site.js` adds two small buttons ("Edit header", "Edit footer") only after the pop-up has been opened once on that page view (`ED.onOpen`). They live in the `#twd-sk-ed` wrapper as fixed-position elements placed over the corner of `.twd-sk-chrome .twd-sk-header` / `.twd-sk-footer` (repositioned on scroll and resize, hidden when that part is off screen), never inside the header or footer, and never printed by PHP, so visitors cannot see them and the site layout is untouched. They exist only where the kit header or footer is printed (the Theme Builder templates are imported). Each calls `ED.openAt('site', fieldId)`: Edit header focuses the Menu box (`twd-sk-pf-menu`), Edit footer the footer text (`twd-sk-pf-footertext`). The Close button, Escape and clicking outside all go through `requestClose()`: it lists anything unsaved and shows an inline card (Keep editing, or Close and lose these changes). Unsaved means pasted page text not applied, plus checks registered with `ED.addDirtyCheck(test, discard)` by the style, site details, header and footer and search sections (each compares a snapshot taken when it was last filled or saved). Losing the changes runs each discard so the live style preview and the form boxes go back to what is saved. There is deliberately no browser leave-page dialog.

## Tests

`php tests/run.php` runs everything. Hand-rolled, zero dependency, one file per area (`tests/test-*.php`), WordPress stubbed in `tests/bootstrap.php`. Exit code is non-zero on any failure. Every sanitiser rule has at least one test. Also run `php -l` on every PHP file before pushing.

## Releases & self-hosted updates

The plugin is not on WordPress.org, so it updates itself (see `TWD_SK_Updater` above). Every client site checks `dist/twd-site-kit-update.json` in **this repo** (must stay **public**: sites fetch it with no credentials) and, if its `version` is newer than the installed one, shows the normal "update available" row in wp-admin Plugins with a one-click update. Checked every 12 hours, or straight away with the "Check for updates" link on the plugin row.

To ship a new version to every site running the plugin:

```bash
# 1. Bump the version in THREE places, all the same: the Version line in the
#    twd-site-kit.php header, the TWD_SK_VERSION constant in the same file, and
#    Stable tag in readme.txt (also add a changelog entry there).

# 2. Run the tests and lint. Every test must pass.
php tests/run.php
for f in twd-site-kit.php includes/*.php bin/*.php tests/*.php; do php -l "$f"; done

# 3. Build the distributable zip and verify it. It must contain a single
#    top-level twd-site-kit/ folder (WordPress's plugin upgrader requires that
#    shape; a zip of the folder's contents silently misinstalls). The script uses
#    cp -r, not rsync, builds fresh, unzips the result, diffs every file against
#    the source, checks the file lists match, and runs the release check.
bash bin/build-zip.sh

# 4. Update the JSON: version, changelog entry, the fixed download address, the
#    sha256 of the zip just built, and today's date. The changelog must start
#    with <h4>VERSION</h4>.
php bin/update-json.php --changelog="<h4>0.2.2</h4><ul><li>What changed.</li></ul>"

# 5. Strict release check. It must print OK: header Version, TWD_SK_VERSION and
#    readme.txt Stable tag agree with the JSON version, the zip holds the same
#    version in one twd-site-kit folder, and the JSON sha256 matches the zip.
php bin/check-release.php

# 6. Commit and push the code, the zip and the JSON together to main.
```

Rules:
- **The zip and the JSON always travel together.** Rebuilding the zip changes its sha256 (zip timestamps), so after any rebuild run step 4 again (for the same version it only refreshes the sha256 and date) and step 5. A test fails if the JSON checksum does not match `dist/twd-site-kit-latest.zip`, so a forgotten step cannot be committed quietly.
- `download_url` in the JSON must be exactly the fixed address, and `dist/twd-site-kit-latest.zip` is a stable path that never changes.
- **No git tags.** The git proxy used in cloud sessions refuses tag pushes. The JSON (version, date, changelog, checksum) is the release record. `git log -- dist/twd-site-kit-update.json` finds the commit for any version.
- **GitHub's raw address caches for a few minutes.** Right after a push the JSON and the zip can briefly be out of step. The updater then fails closed with a checksum message and installs nothing. Wait about five minutes and use "Check for updates" again.
- **Rolling back.** The updater never installs a version that is not newer, so a bad release is fixed by releasing a HIGHER version that carries the older, good code (for example 0.2.3 built from the 0.2.1 code).
- The repo must stay public, and credentials never go in it.

For a one-off manual install (skipping the updater, for example trying a change on a single site): upload `dist/twd-site-kit-latest.zip` via **Plugins > Add New > Upload Plugin**. WordPress offers to replace the installed version.

## Repo rules

- **This repo must stay public.** The self-hosted updater (later) reads releases and `dist/` anonymously. Never put credentials, keys, or client content in it.
- `dist/` holds the install zip (`twd-site-kit-latest.zip`) and the updater's `twd-site-kit-update.json`. The zip contains only the plugin files (no tests, no docs).
- Client site content lives in separate private repos (one per client), never here.
- Do not invent credentials, registration bodies, numbers, fees or claims in any site content. Anything not in the client's own words is a question.
